# code_review_debate — 博弈式代码审查

> **版本**: v1.0 | **日期**: 2026-06-01
> **触发**: `/review`, `/debate`, `博弈审查`, `代码审查`

## 什么是博弈审查？

博弈审查不是被动接受外部报告的结论，而是**逐项验证、挑战假设、提供证据**的对抗性审查方法。

## 核心原则

### 1. 验证优先 (Verify First)
- 外部报告不一定正确——必须对比实际代码
- 每个 Finding 都需要引用具体文件、行号、代码片段
- "已修复" 必须有 git diff 或测试证明

### 2. 博弈思维 (Adversarial Thinking)
- 对每个结论提出反面论证
- 区分 "报告说的" vs "代码实际的"
- 找出报告的盲点和误判

### 3. 证据驱动 (Evidence-Based)
- 每个判断必须有代码证据
- 不接受 "感觉不对" 式评分
- 量化优于定性

### 4. 根因分析 (Root Cause)
- 表面修复 ≠ 根因修复
- 追问 "为什么会这样" 而非 "怎么修"
- 修复不应产生新问题

## 工作流程

```
输入: 外部报告 (HTML/MD) + 代码库
  │
  ├─ Step 1: 解析报告 → 提取所有 Finding
  ├─ Step 2: 逐项验证 → 对比实际代码
  ├─ Step 3: 博弈分析 → AGREED / PARTIAL / DISAGREED
  ├─ Step 4: 修正评分 → 基于证据的加权评分
  └─ Step 5: 输出报告 → 结构化结论 + 行动清单
```

## 输出格式

```markdown
## 博弈审查报告

### 总览
- 报告准确率: X/Y (Z%)
- 修正后评分: X.X/10 (原报告: Y.Y/10)

### 逐项分析

| # | Finding | 报告结论 | 验证结果 | 判定 | 证据 |
|---|---------|---------|---------|------|------|
| 1 | XXX     | P0 Critical | 已修复 | DISAGREED | git commit abc123 |
| 2 | YYY     | P1 High | 确认 | AGREED | file.py:42 |

### 修正评分
| 维度 | 报告评分 | 修正评分 | 差异原因 |
|------|---------|---------|---------|
| 安全 | 4/10 | 8/10 | 6项已修复报告未计入 |

### 行动清单
- [ ] 修复: XXX (P0)
- [ ] 验证: YYY (需补充测试)
- [ ] 忽略: ZZZ (已修复/误报)
```

## 触发示例

```
/review CODE_REVIEW_REPORT.html    → 对外部报告进行博弈审查
/debate OPTIMIZATION_ADVISORY.html → 挑战优化建议
博弈审查 THIRD_REVIEW.html         → 逐项验证第三次审查
```

## 使用场景

1. **Code Review 后**: 收到外部审查报告时，用博弈方法验证
2. **架构评审后**: 挑战优化建议的优先级和可行性
3. **自我审查**: 对自己的修改进行对抗性检查
4. **PR 审查**: 对他人的 PR 进行结构化博弈

## 方法论来源

基于 Inspection V3.2 项目的三轮 Code Review 实战经验:
- Review #1: 36 findings, 28 correct (78%), 2 已修复被标记为 P0
- Review #2: 16 领域建议, 优先级判断需项目上下文
- Review #3: commit 审计, 发现声明与实际变更的差距

关键教训:
- 报告基於旧代码快照时，已修复项会被误标
- SRE 教科書建议不一定适合项目阶段
- "适配器是空壳" vs "部分实现" 是评估粒度问题
